## Intent

**Problem:** The six parts, eight challenge cards, and the mission exist only as tables in `parts-and-cards.md`, so the palette (story 3) and the resolver (story 4) have nothing to read and balance can't be tuned in the inspector (CAP-8).

**Approach:** Define typed Godot Resource classes for parts, cards, and the mission, and author `.tres` files holding the starting values from `parts-and-cards.md`. Every number a rule will read (HP, fuel per tank, shield capacity, hits per card, extra fuel loss, counter thresholds, cargo required) is an inspector field. No rules logic yet.

</frozen-after-approval>

## Implementation Notes

- Resource scripts (plain `Resource`, no Node dependencies) in `scripts/data/`:
  - `PartData`: `kind` enum (THRUSTER, FUEL_TANK, CARGO_HOLD, SHIELD, HULL_PLATING, GUN), `display_name`, `max_hp`, `color` (placeholder tile), `fuel_capacity` (tanks: 4), `shield_capacity` (shields: 2), `required_row` enum (ANY, FRONT, REAR; thruster REAR, gun FRONT).
  - `CardData`: `kind` enum (one per card), `display_name`, `direction` enum (NONE, FRONT, FLANK, REAR, ALL, INTERNAL), `hits` (Pirate 3 — one per front column, Asteroid 2, Debris 1, Rear Raider 1, Solar Flare 1 per part), `extra_fuel_loss` (Fuel Leak 2, Gravity Well 1), `counter_threshold` (Fuel Leak 2 tanks, Gravity Well 2 thrusters), `damage_per_hit` (1), `countered_text` / `uncountered_text` for later log lines.
  - `MissionData`: `display_name`, `cargo_required`, `fuel_per_card` (1), `parts: Array[PartData]` (palette order), `card_pool: Array[CardData]` (the 8-card shuffle pool).
- Card behavior is keyed by `CardData.kind` in story 4; the numbers live in data. The resolver must read these fields, not literals.
- `.tres` files under `data/parts/` (6), `data/cards/` (8), `data/missions/cargo_run.tres` (1). The mission references all parts and cards, so it is the single entry point stories 3–4 load.
- Mission `cargo_required` starts at 2: the spec leaves N open as a data value, and story 7 tunes it.
- No scene changes in this story.
- Pirate Ambush `counter_threshold` = 1 (working front-row guns needed). Its `hits` = 3 means one per front column; story 4 owns the lane logic.
- Script defaults are neutral (`max_hp` 1, `damage_per_hit` 0, `cargo_required` 0). Godot omits fields equal to the default when saving, so neutral defaults keep every starting value written in the `.tres` and stop a later default change from silently changing data.
- Files: `scripts/data/{part,card,mission}_data.gd` (+ `.uid`), `data/parts/*.tres` (6), `data/cards/*.tres` (8), `data/missions/cargo_run.tres`.
- The `.tres` files were generated by a throwaway headless `ResourceSaver` script, not committed. Surprise: `--script` mode does not write `uid=` fields, so a second throwaway pass added Godot-generated UIDs to the headers and `ext_resource` lines, as story 1 did for its scene.
- Verified: headless `--import` and a headless run show no errors or warnings. A headless script loading `cargo_run.tres` prints 6 parts and 8 cards whose values match `parts-and-cards.md`, with cargo_required 2.
- Review patches: removed `cargo_capacity` (the rules count intact holds, not units); added `MissionData.fuel_per_card`; enums marked append-only because `.tres` stores them by number; `kind` defaults flagged as non-neutral (hull_plating.tres and calm_space.tres omit the line); doc comments pin each card's meaning of `hits` and `counter_threshold`.
- project.godot: no settings changed in this story.
